# Anatomy of a Command

You can open a terminal and get a shell to respond.
Now we need to turn a line of mysterious text into something you can read.
What is the command asking for?
Which parts can you change?
Where do you look when you do not recognize a piece?

You do not need to memorize a command encyclopedia.
You need a way to take commands apart and investigate them.
That is the difference between collecting recipes and learning to cook.

The examples in this chapter display text, list files, or ask for information.
They do not create, change, or delete your files.
Use the examples labeled for your shell.
The PowerShell examples work in both Windows PowerShell 5.1 and PowerShell 7.

Remember our console notation: a bold line beginning with `$ ` is a command to enter.
Do not type the `$ ` marker, even if your actual prompt looks completely different.
Unmarked lines show output.
Where the output depends on your computer, we describe what to look for and leave the output out of the box.

## A Name and Some Arguments

Start with the command from Chapter 1.
This simple example works in **Bash/zsh, PowerShell, and Command Prompt**:

```session
$ echo console-ready
console-ready
```

`echo` is the **command name**.
`console-ready` is an **argument**: information supplied to the command.
Here it is the text we want to display.
In other commands, an argument might identify a file, choose a setting, or supply a search term.

For the simple commands we are starting with, read the first word as the command name and the remaining words as its arguments.
Spaces separate those words.
The shell has more rules, including quotation marks that keep spaces inside an argument; we will meet those shortly. [@BashManual]

Changing `console-ready` changes the message.
Changing `echo` asks the shell to do something else.
Those are different kinds of edits, even though both involve replacing text.

## Options Change the Request

An **option** changes how a command behaves.
You will also hear **flag** or **switch**, especially for an option that turns a behavior on without taking another value.
Options are not a separate language understood identically by every command.
Each command has its own accepted names and rules.

Let us ask for a directory listing: the names of files and directories in a location.
Use an ordinary filesystem directory, such as the home folder where your shell started.

### Bash/zsh

`ls` lists directory contents.
The argument `.` means the current directory.
Run these one at a time and compare the results:

```session
$ ls .
$ ls -a .
```

Normally, `ls` leaves out names beginning with a dot.
The `-a` option includes them, along with the special entries `.` and `..`.
We will explore what those entries mean in Chapter 4. [@CoreutilsListedFiles]

Read the second command in pieces:

| Piece | Role | Meaning here |
|---|---|---|
| `ls` | Command name | List directory contents |
| `-a` | Option | Include names normally hidden by their leading dot |
| `.` | Path argument | Look in the current directory |

The option and path are both arguments passed to `ls`, but they do different jobs.
The path says **where**; the option changes **how** the results are selected.

### PowerShell

`Get-ChildItem` lists the items inside a location.
For a filesystem directory, those items are files and subdirectories.

```session
$ Get-ChildItem -Path .
$ Get-ChildItem -Path . -Force
```

PowerShell calls these named controls **parameters**.
`-Path` takes a value: the `.` immediately after it.
`-Force` is a **switch parameter**; here, it includes hidden items that the normal listing leaves out.
It does not bypass access permissions. [@PowerShellGetChildItem]

Read `-Path .` as a pair: parameter name, then its argument value.
The long names make the request readable once you know where the pieces begin and end.

### Command Prompt

In `cmd.exe`, `dir` lists directory contents.

```session
$ dir .
$ dir /a .
```

The `/a` option includes entries with hidden or system attributes that the default listing omits.
With no attribute selection after `/a`, it includes all attribute types. [@WindowsDir]

The three pairs of commands have a similar purpose, but their output formats and definitions of hidden files differ.
Do not expect identical listings just because the requests sound similar in English.

::: {.tip}
**Trap:** An option belongs to a particular command, not to your terminal window.
`-a`, `-Force`, and `/a` are not interchangeable spellings.
Changing shells can also change which command a familiar name selects.
:::

### Short Names Are Not a Universal Code

Many UNIX tools use a single hyphen for short options, such as `-a`, and two for longer names, such as `--all`.
GNU `ls`, commonly found on Linux, accepts `--all` as another spelling of `-a`.
Do not assume every system's `ls` accepts the same long options. [@CoreutilsListedFiles]

PowerShell's full parameter names normally use one hyphen, as in `-Path`.
Many traditional Windows commands use a slash, as in `/a`.
An external program can use its own conventions regardless of which shell launches it.

You will sometimes see short options combined, but do not combine letters just because a command looks shorter that way.
First check that command's help.
And do not assume a word like *force* has the same consequences everywhere: showing hidden entries is very different from forcing an overwrite.

## Spaces Can Be Part of an Argument

Suppose your message is `console punk`, with a space.
You need a way to say that the space belongs inside the text rather than separating two arguments.
Quotation marks provide that grouping.

### Bash/zsh

`echo` is not a good argument counter: it puts spaces between the arguments it prints.
For this experiment, use `printf`, which prints according to a **format string**.
In `'<%s>\n'`, `%s` marks a string to insert, `<` and `>` make its boundaries visible, and `\n` requests a new line.
The format is reused for the remaining values. [@BashBuiltins]

```session
$ printf '<%s>\n' console punk
<console>
<punk>
$ printf '<%s>\n' "console punk"
<console punk>
```

Without the quotation marks, `console` and `punk` are separate arguments after the format string.
With them, `console punk` is one argument containing a space.
The grouping quotation marks themselves are not part of that value.

### PowerShell

`Write-Output` writes values to PowerShell's output stream.
Here, the value is one **string**, meaning a piece of text:

```session
$ Write-Output "console punk"
console punk
```

The quotation marks keep the two words together as one string. [@PowerShellQuoting]
In a default PowerShell session, the familiar name `echo` is an alias for `Write-Output`.
We will unpack aliases in a moment. [@PowerShellWriteOutput]

### Command Prompt

Command Prompt has different parsing rules, and its built-in `echo` treats the following message differently from the UNIX `printf` example.
For the simple message here, enter:

```session
$ echo console punk
console punk
```

Do not use this result to infer how another command handles spaces.
For a path containing spaces, use double quotation marks around the path, such as `"C:\Program Files"`.
Single quotation marks are not a substitute for double quotation marks in Command Prompt. [@WindowsCmd; @WindowsEcho]

We will study quoting and special characters properly in Chapter 8.
For now, use the quotation marks shown in the example for your shell, and keep the opening and closing marks paired.
If an unfinished quote leaves Bash, zsh, or PowerShell waiting for more input, press `Ctrl+C` to cancel and start again.

## Paths Are Arguments Too

A **path** identifies a location in the filesystem.
It can refer to a file or a directory.
In our listings, `.` is a short path meaning the current directory.

An **absolute path** starts from a filesystem root, such as `/usr` on a UNIX-style system or `C:\Windows` on Windows.
A **relative path** starts from your current directory, such as `notes.txt` or `./notes.txt` in a UNIX shell and `.\notes.txt` in a Windows shell.
These are illustrations, not files you need to have yet.

That gives you another useful question when reading a command: **relative to where?**
The same relative path can identify different files when you run a command from different directories.

The role matters too.
A path supplied to a listing command tells it what to inspect; it does not move your shell into that directory.
Changing directories is a separate operation, which we will learn in Chapter 4.

## What Does That Name Actually Run?

Not every command is a separate program on disk.
A name can lead to several different kinds of thing:

- A **built-in** is implemented by the shell itself. Bash and zsh provide a built-in `echo`; Command Prompt has its own internal `echo` and `dir` commands.
- An **external program** is a separate executable the shell starts. The usual UNIX `ls` is an example.
- An **alias** gives a command another name or, in shells such as Bash and zsh, substitutes text into the command line.
- A **function** is a named piece of shell code. We will write our own later.
- A **cmdlet**, pronounced *command-let*, is a command designed for PowerShell's command system. `Get-ChildItem` and `Write-Output` are examples.

Bash documents the distinction between its built-ins and separate programs; PowerShell's command discovery distinguishes aliases, functions, cmdlets, and applications. [@BashShellBuiltins; @PowerShellGetCommand]

PowerShell cmdlet names conventionally use a **Verb-Noun** pattern.
`Get-ChildItem` gets child items; `Get-Command` gets information about commands.
The hyphen inside the name is part of the name, not an option separator.

### Ask Bash or zsh

`type` reports how the shell interprets a command name.

```session
$ type echo
```

In an uncustomized Bash or zsh session, it reports that `echo` is a shell built-in.
Your shell can report an alias or function instead if your configuration defines one.

Add `-a` to look for all the matches `type` can find:

```session
$ type -a ls
```

You may see a path to an executable, several paths, or an alias as well.
The exact wording and paths depend on your shell and installation. [@BashBuiltins; @ZshBuiltins]

### Ask PowerShell

`Get-Command` reports what kind of command a name selects.

```session
$ Get-Command echo
$ Get-Command Get-ChildItem
$ Get-Command dir
```

Look at the `CommandType` and `Name` columns.
With the default aliases, `echo` points to `Write-Output`, while `dir` points to `Get-ChildItem`.
`Get-ChildItem` itself is a cmdlet.
Use `Get-Command dir -All` to investigate multiple commands sharing that name. [@PowerShellGetCommand; @PowerShellGetChildItem]

::: {.tip}
**Wut:** PowerShell's `dir` is not Command Prompt's `dir`.
The default PowerShell alias selects `Get-ChildItem`, so it expects that cmdlet's parameters, not Command Prompt's `/a` syntax.
A familiar name is a clue, not a guarantee of familiar behavior.
:::

### Ask Command Prompt

`help` lists many of Command Prompt's available commands and describes their use.
For a particular command, give its name:

```session
$ help dir
```

For external program files, `where.exe` searches the current directory and the directories listed in `PATH`.
For example, find the Command Prompt executable:

```session
$ where.exe cmd.exe
```

This reports matching file paths, not internal commands or shell aliases.
Failure to find an `echo.exe` would not mean Command Prompt lacks its internal `echo`. [@WindowsHelp; @WindowsWhere]

### Finding Programs Is Not Searching the Whole Computer

`PATH` is a setting containing directories to search for executable commands.
It is not an index of every program you have installed.
Shells also have their own rules for resolving aliases, functions, and other command types.

PowerShell normally does not run a program from the current directory by its bare name unless that directory is on `PATH`.
An explicit relative path, such as `.\tool.exe`, identifies it there.
Bash and zsh commonly use `./tool` for the same purpose; Command Prompt normally searches the current directory too. [@PowerShellCommandPrecedence; @BashCommandSearch; @WindowsCmd]

Those paths are examples of notation, not instructions to run an unknown file.
Only run programs you intend to trust.
We will handle installation and `PATH` configuration in Chapter 10.

## Help Is a Tool, Not a Defeat

Knowing how to ask a command about itself is more useful than remembering every option.
Different command types have different help systems.

### Bash/zsh

In **Bash**, `help` describes built-in commands:

```session
$ help echo
```

That is Bash's help system, not a universal command available in every shell.
For **zsh**, its built-in commands are documented together in the `zshbuiltins` manual:

```session
$ man zshbuiltins
```

In **either shell**, use the installed manual for a program such as `ls`:

```session
$ man ls
```

`man` opens a **manual page**, usually in a **pager** that lets you move through text a screen at a time.
With the common `less` pager, use Space for the next screen, Up and Down Arrow to move a line, and `q` to quit. [@LessManual]
Different pager settings can change those keys.
If `man` or the requested page is not installed, consult the tool's official documentation instead.

GNU `ls` also accepts `ls --help`.
That is a feature of that program; `--help` is not a magic request that works with everything.

### PowerShell

`Get-Help` reads help for a command.
Start with an overview, then ask for examples:

```session
$ Get-Help Get-ChildItem
$ Get-Help Get-ChildItem -Examples
```

If the local help files are missing, you may get only basic syntax rather than the full explanation.
`Get-Help Get-ChildItem -Online` opens the online documentation in your browser and needs internet access.
You do not need to change system settings just to read that page. [@PowerShellGetHelp]

### Command Prompt

Use `help` for a list, then ask about the command you want:

```session
$ help
$ help dir
$ dir /?
```

For `dir`, the last two forms show its help.
Many Windows utilities recognize `/?`, but an independently installed program may use something else.
Check that program's documentation instead of trying random switches. [@WindowsHelp; @WindowsDir]

## Read the Shape Before the Details

Help often begins with a **syntax** or **synopsis** line.
It describes the allowed shape of a command, rather than giving you a line to paste unchanged.

For example, Bash's `help echo` includes this syntax fragment:

```{.text .no-copy}
echo [-neE] [arg ...]
```

The brackets mark optional pieces.
`arg` stands for an argument you supply, and `...` indicates that arguments can be repeated.
You do not type the brackets, the word `arg`, or the dots literally.

Windows documentation also uses square brackets for optional pieces and angle brackets for values you supply, such as `<command>`.
Read the syntax key when the notation is unfamiliar. [@WindowsSyntaxKey]

In PowerShell help, a fragment such as `[-Path] <String[]>` has an extra distinction: the parameter name can be omitted when its value is supplied in the appropriate position.
`String[]` means the value can be an array of strings; those inner brackets do not mean "optional".
For now, keep writing `-Path` explicitly so the command explains itself. [@PowerShellHelpSyntax]

::: {.tip}
**Tip:** Read help with a question in mind.
Find the command's purpose, identify the argument or option you need, and read one relevant example.
Predict what your version will do before you run it.
You can return for the other options when you have a reason to use them.
:::

## Key Points

- A command name selects an action; arguments provide information for that action.
- Options and parameters change the request, and their syntax belongs to the command you are using.
- Quotation marks can keep spaces inside an argument, but quoting rules differ across shells.
- A path identifies a location; relative paths depend on the current directory.
- A name may select a built-in, external program, alias, function, or PowerShell cmdlet.
- Use `type`, `Get-Command`, or Command Prompt's help and file-location tools to investigate names.
- Read help as a description of valid commands, not as text to paste without interpretation.

## Level Up

n00bs finish the chapter here.
You can point to the pieces of a command and find help for the ones you do not understand.
Hackers start checking their assumptions about what actually runs.

Choose one command you have used in this chapter and investigate its identity.
In Bash or zsh, compare `type echo` with `type -a echo`.
In PowerShell, inspect `Get-Command echo -All` and compare the result with `Get-Command Write-Output`.
In Command Prompt, compare what `help echo` tells you with what `where.exe cmd.exe` can find.
Explain why a help topic, an alias, and an executable path are different kinds of answer.

Then choose one listing option from the help for `ls`, `Get-ChildItem`, or `dir` that changes only the display or selection of entries.
Predict the difference, run the command, and explain what changed.
Can you make a similar request in another shell without assuming it uses the same syntax?

Keep a small note containing the command, what each part means, and where you found the explanation.
That is the beginning of a reference you understand, not just a collection of things to paste.
