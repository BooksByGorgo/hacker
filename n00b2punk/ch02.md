# Anatomy of a Command

You can open a terminal and get a shell to respond.
Now we will use commands to do things.
You do not need to memorize a command encyclopedia, but you should learn a core set of commands that you use frequently; `echo` is one of them.
Knowing the right command to use with the right arguments at the right time is a big part of hacking.

The examples in this chapter display text, list files, or ask for information.
They do not create, change, or delete your files.
Use the examples labeled for your shell.
The PowerShell examples work in both Windows PowerShell 5.1 and PowerShell 7.

Remember our console notation: a bold line beginning with `$ ` is a command to enter.
Do not type the `$ ` marker, even if your actual prompt looks completely different.
Unmarked lines show output.
Where the output depends on your computer, we describe what to look for and leave the output out of the box.

The concepts in this chapter are:

- **command names**, **arguments**, and **options**;
- **quoting** and **escaping**, which keep spaces and special characters inside an argument;
- what the shell changes before a program runs: **variables**, **command substitution**, **wildcards**, and **quote removal**;
- the kinds of thing a name can select: **built-ins**, **external programs**, **aliases**, **functions**, and **cmdlets**;
- the **environment**, **PATH**, and how the shell finds a program;
- **package managers**, installation, and version conflicts;
- **help** and how to read a syntax line.

## A Name and Some Arguments

Start with the command from Chapter 1.
This simple example works in **Bash/zsh, PowerShell, and Command Prompt**:

```session
$ echo console-ready
console-ready
```

`echo` is the **command name**.
`console-ready` is an **argument**: information supplied to the command.
Here it is the text we want to display.
In other commands, an argument might identify a file, choose a setting, or supply a search term.

For the simple commands we are starting with, read the first word as the command name and the remaining words as its arguments.
Spaces separate those words.
The shell has more rules, including quotation marks that keep spaces inside an argument; we will see those shortly. [@BashManual]

Changing `console-ready` changes the message.
Changing `echo` asks the shell to do something else.

## Options Change the Request

An **option** changes how a command behaves.
You will also hear **flag** or **switch**, especially for an option that turns a behavior on without taking another value.
Options are not a separate language understood identically by every command.
Each command has its own accepted names and rules.

Let's ask for a directory listing: the names of files and directories in a folder.
Use an ordinary filesystem directory, such as the home folder where your shell started.

### Bash/zsh

`ls` lists directory contents.
The argument `.` means the current directory.
Run these one at a time and compare the results:

```session
$ ls .
$ ls -a .
```

Normally, `ls` leaves out names beginning with a dot.
The `-a` option includes them, along with the special entries `.` and `..`.
We will explore what those entries mean in Chapter 3. [@CoreutilsListedFiles]

Read the second command in pieces:

| Piece | Role | Meaning here |
|---|---|---|
| `ls` | Command name | List directory contents |
| `-a` | Option | Include names normally hidden by their leading dot |
| `.` | Path argument | Look in the current directory |

The option and path are both arguments passed to `ls`, but they do different jobs.
The path says **where**; the option changes **how** the results are selected.

### PowerShell

`Get-ChildItem` lists the items inside a location.
For a filesystem directory, those items are files and subdirectories.

```session
$ Get-ChildItem -Path .
$ Get-ChildItem -Path . -Force
```

PowerShell calls these named controls **parameters**.
`-Path` takes a value: the `.` immediately after it.
`-Force` is a **switch parameter**; here, it includes hidden items that the normal listing leaves out.
It does not bypass access permissions. [@PowerShellGetChildItem]

Read `-Path .` as a pair: parameter name, then its argument value.
The long names make the request readable once you know where the pieces begin and end.

### Command Prompt

In `cmd.exe`, `dir` lists directory contents.

```session
$ dir .
$ dir /a .
```

The `/a` option includes entries with hidden or system attributes that the default listing omits.
With no attribute selection after `/a`, it includes all attribute types. [@WindowsDir]

The three pairs of commands have a similar purpose, but their output formats and definitions of hidden files differ.
Do not expect identical listings just because the requests sound similar in English.

::: {.tip}
**Trap:** An option belongs to a particular command, not to your terminal window.
`-a`, `-Force`, and `/a` are not interchangeable spellings.
Changing shells can also change which command a familiar name selects.
:::

### Short Names Are Not a Universal Code

Many UNIX tools use a single hyphen for short options, such as `-a`, and two for longer names, such as `--all`.
GNU `ls`, commonly found on Linux, accepts `--all` as another spelling of `-a`.
Do not assume every system's `ls` accepts the same long options. [@CoreutilsListedFiles]

PowerShell's full parameter names normally use one hyphen, as in `-Path`.
Many traditional Windows commands use a slash, as in `/a`.
An external program can use its own conventions regardless of which shell launches it.

You will sometimes see short options combined, but do not combine letters just because a command looks shorter that way.
First check that command's help.
And do not assume a word like *force* has the same consequences everywhere: showing hidden entries is very different from forcing an overwrite.

## Spaces Can Be Part of an Argument

Suppose your message is `console punk`, with a space.
You need a way to say that the space belongs inside the text rather than separating two arguments.
Quotation marks provide that grouping.

### Bash/zsh

`echo` is not a good argument counter: it puts spaces between the arguments it prints.
For this experiment, use `printf`, which prints according to a **format string**.
In `'<%s>\n'`, `%s` marks a string to insert, `<` and `>` make its boundaries visible, and `\n` requests a new line.
The format is reused for the remaining values. [@BashBuiltins]

```session
$ printf '<%s>\n' console punk
<console>
<punk>
$ printf '<%s>\n' "console punk"
<console punk>
```

Without the quotation marks, `console` and `punk` are separate arguments after the format string.
With them, `console punk` is one argument containing a space.
The grouping quotation marks themselves are not part of that value.

#### Other Ways to Keep a Space

Single quotes also group this text into one argument.
Alternatively, a backslash can **escape** an unquoted space: tell the shell to treat it as a literal character instead of a separator.
You can even join unquoted and quoted pieces without putting a separating space between them:

```session
$ printf '<%s>\n' 'console punk'
<console punk>
$ printf '<%s>\n' console\ punk
<console punk>
$ printf '<%s>\n' console" punk"
<console punk>
```

All three pass the same value after the format string.
The backslash in `console\ punk` is shell syntax; it is not part of the resulting text. [@BashQuoting; @ZshQuoting]

#### Quotes Inside the Text

Use the other kind of quote around a string that contains quotation marks:

```session
$ printf '%s\n' 'say "hello"'
say "hello"
$ printf '%s\n' "it's working"
it's working
```

Inside double quotes, `\"` includes a literal double quote:

```session
$ printf '%s\n' "say \"hello\""
say "hello"
```

A backslash does not escape an apostrophe inside ordinary single quotes.
Use double quotes around that text, as in `"it's working"`, instead.
Single and double quotes are not interchangeable for every string: double quotes still allow substitutions such as variable values.
The next section shows those substitutions. [@BashQuoting; @ZshQuoting]

### PowerShell

`Write-Output` writes values to PowerShell's output stream.
Here, the value is one **string**, meaning a piece of text:

```session
$ Write-Output "console punk"
console punk
```

The quotation marks keep the two words together as one string. [@PowerShellQuoting]
In a default PowerShell session, the familiar name `echo` is an alias for `Write-Output`.
We will unpack aliases in a moment. [@PowerShellWriteOutput]

#### Other Ways to Keep a Space

Single quotes also work for this message.
PowerShell's escape character is the **backtick**, not the backslash; a backtick immediately before an unquoted space keeps it in the argument:

```session
$ Write-Output 'console punk'
console punk
$ Write-Output console` punk
console punk
```

The backtick is different from the apostrophe used for single quotes.
Quoting the whole string is usually easier to read. [@PowerShellParsing]

#### Quotes Inside the Text

As in Bash/zsh, the other kind of quotation mark can appear inside the surrounding pair:

```session
$ Write-Output 'say "hello"'
say "hello"
$ Write-Output "it's working"
it's working
```

Inside a double-quoted string, escape a double quote with a backtick.
Inside a single-quoted string, write an apostrophe twice to include one literal apostrophe:

```session
$ Write-Output "say `"hello`""
say "hello"
$ Write-Output 'it''s working'
it's working
```

Single-quoted strings are literal; double-quoted strings allow substitutions such as variable values.
These examples use a PowerShell cmdlet.
Passing embedded quotes to external programs has additional rules and version differences; do not assume the same spelling works everywhere. [@PowerShellQuoting; @PowerShellParsing]

### Command Prompt

Command Prompt has different parsing rules, and its built-in `echo` treats the following message differently from the UNIX `printf` example.
For the simple message here, enter:

```session
$ echo console punk
console punk
```

Do not use this result to infer how another command handles spaces.
For a path containing spaces, use double quotation marks around the path, such as `"C:\Program Files"`.
Single quotation marks are not a substitute for double quotation marks in Command Prompt. [@WindowsCmd; @WindowsEcho]

Unlike Bash's `echo` or PowerShell's `Write-Output`, Command Prompt's internal `echo` keeps double quotation marks in the displayed message:

```session
$ echo say "hello"
say "hello"
$ echo "console punk"
"console punk"
```

This is useful for displaying quotes, but it is not a general rule for passing quoted text to other programs.
Command Prompt uses the caret (`^`) to escape certain special characters, but a caret before a space is not a reliable replacement for quoting an argument to an external program.
Keep using double quotes around paths with spaces, and consult the target program's rules for embedded quotes. [@WindowsCmd; @WindowsArgumentParsing]

::: {.tip}
**Trap:** Escape characters are shell-specific.
Bash/zsh use a backslash; PowerShell uses a backtick; Command Prompt uses a caret for some purposes.
Copying an escape from another shell can change the text or split an argument instead of protecting it.
:::

Use the quotation marks shown in the example for your shell, and keep the opening and closing marks paired.
If an unfinished quote leaves Bash, zsh, or PowerShell waiting for more input, press `Ctrl+C` to cancel and start again.

## What the Shell Does to Your Command

The quotation marks in the previous section disappeared before the program saw its argument.
That is one example of a general rule: the shell reads your line, transforms parts of it, and only then runs the command with the results.
The program never sees your quotes, your variable names, or your wildcards.
It sees the arguments the shell produced.

The transformations you will meet most often are:

- **Variable expansion** replaces a variable reference with its stored value.
- **Command substitution** runs another command and replaces the reference with its output.
- **Filename expansion**, also called **globbing**, replaces a pattern such as `*.md` with the matching filenames. Bash and zsh do this; PowerShell and Command Prompt leave the pattern for the command to interpret.
- **Quote removal** strips the quotation marks and escape characters that controlled the other steps.

Quotes control which transformations happen.
Every shell has a way to say "expand this" and "leave this alone", but the spelling differs, so learn the rules for the shell you are using.

### Bash/zsh

`printf '<%s>\n'` shows exactly which arguments a program received, so keep using it as a probe.

A **variable** stores a value under a name.
`HOME` holds the path to your home directory, and `$HOME` asks for its value.
Compare three spellings:

```session
$ printf '<%s>\n' $HOME "$HOME" '$HOME'
</home/student>
</home/student>
<$HOME>
```

Unquoted and double-quoted references are both expanded.
Single quotes turn expansion off, so the program receives the five characters `$HOME` unchanged.
The difference between the first two forms appears when the value contains spaces: unquoted, the shell splits it into several arguments; inside double quotes, it stays one argument.
Use `"$HOME"` by default. [@BashShellExpansions; @BashQuoting; @ZshExpansion]

`$(...)` runs a command and substitutes its output:

```session
$ printf '<%s>\n' "$(date +%Y)"
<2026>
```

Your year will differ.
The point is that `date` ran first and `printf` received its output as an argument. [@BashCommandSubstitution]

A **wildcard** pattern is expanded by the shell into matching names.
`*` matches any run of characters within a name.
Try this in a directory containing Markdown files, or read the output as an illustration:

```session
$ printf '<%s>\n' *.md
<notes.md>
<todo.md>
$ printf '<%s>\n' '*.md'
<*.md>
```

The program never sees `*.md` in the first command; it receives one argument per matching file.
With quotes, it receives the literal pattern. [@BashFilenameExpansion]

Bash and zsh disagree about a pattern that matches nothing.
Bash passes the pattern through unchanged, so the program receives `*.zzz`.
zsh reports `no matches found` and does not run the command at all, unless you change its `NOMATCH` option. [@BashFilenameExpansion; @ZshOptions]

::: {.tip}
**Trap:** A wildcard is expanded before the command sees it, so a typo changes which files a command touches.
`rm * .bak` with an accidental space names every file in the directory, not the `.bak` files.
Before running a destructive command with a wildcard, run `printf '<%s>\n'` with the same pattern to see what the shell will pass.
:::

### PowerShell

PowerShell uses a `$` prefix for variables and expands them inside double quotes but not single quotes:

```session
$ Write-Output $HOME
C:\Users\student
$ Write-Output "$HOME"
C:\Users\student
$ Write-Output '$HOME'
$HOME
```

`$(...)` inside a double-quoted string is a **subexpression**: PowerShell evaluates it and inserts the result. [@PowerShellQuoting; @PowerShellVariables]

```session
$ Write-Output "Year: $(Get-Date -Format yyyy)"
Year: 2026
```

To see which arguments a command received, run a **script block** with `&` and print its `$args`:

```session
$ & { foreach ($a in $args) { "<$a>" } } console punk "console punk"
<console>
<punk>
<console punk>
```

You do not need to understand the loop yet; treat it as a probe like `printf` above. [@PowerShellAutomaticVariables]

Use the same probe with a wildcard:

```session
$ & { foreach ($a in $args) { "<$a>" } } *.md
<*.md>
```

PowerShell did not expand the pattern.
Cmdlets such as `Get-ChildItem` interpret wildcards in their own parameters, which is why `Get-ChildItem *.md` lists matching files and why `-LiteralPath` exists to switch that off. [@PowerShellWildcards]

External programs receive the arguments PowerShell built, with its own rules for quotes.
`--%` stops PowerShell parsing the rest of the line and passes it to the program almost as typed; it exists for cases where those rules get in the way. [@PowerShellParsing]

### Command Prompt

Command Prompt reads a variable with percent signs, and it has no quote that switches expansion off:

```session
$ echo %USERPROFILE%
C:\Users\student
$ echo "%USERPROFILE%"
"C:\Users\student"
```

Both forms expand the variable; the quotation marks stay in the output because `echo` displays its text as written.
`^` escapes characters such as `&` and `|`, which otherwise have a special meaning that we return to in Chapter 7. [@WindowsCmd; @WindowsSet]

Command Prompt does not expand wildcards for you.
`dir *.md` works because `dir` interprets the pattern itself.
An external program receives `*.md` literally and decides what to do with it.

::: {.tip}
**Wut:** The same line can mean three things in three shells.
`echo $HOME` prints your home directory in Bash, zsh, and PowerShell, but Command Prompt prints the text `$HOME` because `$` is not special there.
`echo %HOME%` is a variable reference in Command Prompt and plain text in Bash and zsh.
:::

## What Does That Name Actually Run?

Not every command is a separate program on disk.
A name can lead to several different kinds of thing:

- A **built-in** is implemented by the shell itself. Bash and zsh provide a built-in `echo`; Command Prompt has its own internal `echo` and `dir` commands.
- An **external program** is a separate executable the shell starts. The usual UNIX `ls` is an example.
- An **alias** gives a command another name or, in shells such as Bash and zsh, substitutes text into the command line.
- A **function** is a named piece of shell code. We will write our own later.
- A **cmdlet**, pronounced *command-let*, is a command designed for PowerShell's command system. `Get-ChildItem` and `Write-Output` are examples.

Bash documents the distinction between its built-ins and separate programs; PowerShell's command discovery distinguishes aliases, functions, cmdlets, and applications. [@BashShellBuiltins; @PowerShellGetCommand]

PowerShell cmdlet names conventionally use a **Verb-Noun** pattern.
`Get-ChildItem` gets child items; `Get-Command` gets information about commands.
The hyphen inside the name is part of the name, not an option separator.

### Ask Bash or zsh

`type` reports how the shell interprets a command name.

```session
$ type echo
```

In an uncustomized Bash or zsh session, it reports that `echo` is a shell built-in.
Your shell can report an alias or function instead if your configuration defines one.

Add `-a` to look for all the matches `type` can find:

```session
$ type -a ls
```

You may see a path to an executable, several paths, or an alias as well.
The exact wording and paths depend on your shell and installation. [@BashBuiltins; @ZshBuiltins]

### Ask PowerShell

`Get-Command` reports what kind of command a name selects.

```session
$ Get-Command echo
$ Get-Command Get-ChildItem
$ Get-Command dir
```

Look at the `CommandType` and `Name` columns.
With the default aliases, `echo` points to `Write-Output`, while `dir` points to `Get-ChildItem`.
`Get-ChildItem` itself is a cmdlet.
Use `Get-Command dir -All` to investigate multiple commands sharing that name. [@PowerShellGetCommand; @PowerShellGetChildItem]

::: {.tip}
**Wut:** PowerShell's `dir` is not Command Prompt's `dir`.
The default PowerShell alias selects `Get-ChildItem`, so it expects that cmdlet's parameters, not Command Prompt's `/a` syntax.
A familiar name is a clue, not a guarantee of familiar behavior.
:::

### Ask Command Prompt

`help` lists many of Command Prompt's available commands and describes their use.
For a particular command, give its name:

```session
$ help dir
```

For external program files, `where.exe` searches the current directory and the directories listed in `PATH`.
For example, find the Command Prompt executable:

```session
$ where.exe cmd.exe
```

This reports matching file paths, not internal commands or shell aliases.
Failure to find an `echo.exe` would not mean Command Prompt lacks its internal `echo`. [@WindowsHelp; @WindowsWhere]

### Finding Programs Is Not Searching the Whole Computer

`PATH` is a setting containing directories to search for executable commands.
It is not an index of every program you have installed.
Shells also have their own rules for resolving aliases, functions, and other command types.

PowerShell normally does not run a program from the current directory by its bare name unless that directory is on `PATH`.
An explicit relative path, such as `.\tool.exe`, identifies it there.
Bash and zsh commonly use `./tool` for the same purpose; Command Prompt normally searches the current directory too. [@PowerShellCommandPrecedence; @BashCommandSearch; @WindowsCmd]

## Your Environment and Your Tools

A variable such as `HOME` did not come from your typing.
It was handed to the shell when it started, and the shell hands it on to every program it runs.
That inherited set of name-value pairs is the **environment**.

- An **environment variable** is inherited by child programs. `HOME` and `PATH` are examples.
- A **shell variable** exists only inside the shell that created it, unless you export it.
- `PATH` lists the directories the shell searches, in order, when you type a command name that is not built in.
- A **package manager** installs software, usually into directories already on `PATH`, and tracks versions so it can update or remove them.

These rules explain several common surprises: a variable set in one window is missing in another, a freshly installed tool is "not found", and `python` runs a different version than you expected.

### See the Environment

**Bash/zsh:**

```session
$ printenv HOME
$ env
```

`printenv` prints one variable; `env` with no arguments lists them all.
A shell variable is created with `NAME=value` and becomes an environment variable when you `export` it: [@CoreutilsEnv; @BashEnvironment]

```session
$ DEMO=hello
$ bash -c 'echo "child sees [$DEMO]"'
child sees []
$ export DEMO
$ bash -c 'echo "child sees [$DEMO]"'
child sees [hello]
```

`bash -c` starts a child shell to run one command, which shows what a program started from this shell would inherit.
The single quotes keep `$DEMO` from being expanded by the parent before the child runs.

**PowerShell:**

```session
$ $env:HOME
$ Get-ChildItem Env:
```

PowerShell exposes the environment as the `Env:` drive, and `$env:NAME` reads or sets one variable.
Assigning `$env:DEMO = "hello"` creates an environment variable that child programs inherit; an ordinary `$demo = "hello"` variable stays inside PowerShell. [@PowerShellEnvironmentVariables]

**Command Prompt:**

```session
$ echo %USERPROFILE%
$ set
```

`set` with no arguments lists the environment, and `set DEMO=hello` creates a variable in this session.
Command Prompt has no separate shell variables; everything `set` creates is inherited by child programs. [@WindowsSet]

Changes made this way last only until the session ends.
Chapter 10 covers startup files that make settings persistent.

### PATH and Command Lookup

When you type a name that is not a built-in, alias, or function, the shell walks `PATH` from first directory to last and runs the first matching executable.

**Bash/zsh:**

```session
$ echo "$PATH"
$ command -v ls
/usr/bin/ls
```

`PATH` uses `:` between directories.
`command -v` reports what the name resolves to; `type -a` from earlier lists every candidate. [@BashCommandSearch]

**PowerShell:**

```session
$ $env:PATH
$ (Get-Command ls).Source
```

On Windows, `PATH` uses `;` between directories; PowerShell on Linux and macOS uses `:`.
`Get-Command` shows the path in its `Source` property. [@PowerShellCommandPrecedence]

**Command Prompt:**

```session
$ echo %PATH%
$ where.exe notepad.exe
```

`where.exe` searches the current directory and then `PATH`, so it finds the program Command Prompt would run. [@WindowsWhere]

Two consequences follow:

- A directory added to `PATH` by an installer is seen only by shells started after the change. Open a new tab when a freshly installed tool is not found.
- Order matters. When two installations of the same program are both on `PATH`, the first one wins.

### Package Managers

A **package manager** downloads software from a catalog, installs it, records what it installed, and can update or remove it later.
Prefer one over downloading installers by hand: it puts programs on `PATH` consistently and tells you what version you have.

| Platform | Package manager | Install example |
|---|---|---|
| Debian, Ubuntu | APT | `sudo apt install ripgrep` |
| Fedora | DNF | `sudo dnf install ripgrep` |
| macOS | Homebrew | `brew install ripgrep` |
| Windows | winget | `winget install BurntSushi.ripgrep.MSVC` |

`sudo` runs a command with administrator rights, which system-wide installation on Linux needs; Chapter 8 explains it.
Homebrew and winget are separate projects from the operating system and use their own catalogs. [@DebianApt; @HomebrewInstall; @WingetOverview]

Programming languages bring their own package managers, such as `pip` for Python and `npm` for JavaScript.
They install libraries for that language, sometimes with command-line tools, into directories that may or may not be on `PATH`.

### Version Conflicts

Installing a program does not remove other copies.
Getting a different answer from `python3 --version` in two shells is a `PATH` difference, not a broken installation.

Diagnose it with the lookup tools above:

```session
$ type -a python3
```

In PowerShell, `Get-Command python -All`, and in Command Prompt, `where.exe python`, list every candidate in `PATH` order.
The first line is the one that runs.
Fixing the order is a `PATH` edit in a startup file, which Chapter 10 covers.
For now, run the copy you want by its full path when the order surprises you.

::: {.tip}
**Tip:** When a tutorial's command is "not found", ask three questions in order.
Is it installed, is its directory on `PATH` in this shell, and is another program with the same name earlier on `PATH`?
The answers come from your package manager, `echo "$PATH"` or its equivalent, and `type -a` or its equivalent.
:::

## Help Is a Tool, Not a Defeat

Knowing how to ask a command about itself is more useful than remembering every option.
Different command types have different help systems.

### Bash/zsh

In **Bash**, `help` describes built-in commands:

```session
$ help echo
```

That is Bash's help system, not a universal command available in every shell.
For **zsh**, its built-in commands are documented together in the `zshbuiltins` manual:

```session
$ man zshbuiltins
```

In **either shell**, use the installed manual for a program such as `ls`:

```session
$ man ls
```

`man` opens a **manual page**, usually in a **pager** that lets you move through text a screen at a time.
With the common `less` pager, use Space for the next screen, Up and Down Arrow to move a line, and `q` to quit. [@LessManual]
Different pager settings can change those keys.
If `man` or the requested page is not installed, consult the tool's official documentation instead.

GNU `ls` also accepts `ls --help`.
That is a feature of that program; `--help` is not a magic request that works with everything.

### PowerShell

`Get-Help` reads help for a command.
Start with an overview, then ask for examples:

```session
$ Get-Help Get-ChildItem
$ Get-Help Get-ChildItem -Examples
```

If the local help files are missing, you may get only basic syntax rather than the full explanation.
`Get-Help Get-ChildItem -Online` opens the online documentation in your browser and needs internet access.
You do not need to change system settings just to read that page. [@PowerShellGetHelp]

### Command Prompt

Use `help` for a list, then ask about the command you want:

```session
$ help
$ help dir
$ dir /?
```

For `dir`, the last two forms show its help.
Many Windows utilities recognize `/?`, but an independently installed program may use something else.
Check that program's documentation instead of trying random switches. [@WindowsHelp; @WindowsDir]

## Read the Syntax Before the Details

Help often begins with a **syntax** or **synopsis** line.
It describes the allowed usage of a command, rather than giving you a line to paste unchanged.

For example, Bash's `help echo` includes this syntax fragment:

```{.text .no-copy}
echo [-neE] [arg ...]
```

The brackets mark optional pieces.
`arg` stands for an argument you supply, and `...` indicates that arguments can be repeated.
You do not type the brackets, the word `arg`, or the dots literally.

Windows documentation also uses square brackets for optional pieces and angle brackets for values you supply, such as `<command>`.
Read the syntax key when the notation is unfamiliar. [@WindowsSyntaxKey]

In PowerShell help, a fragment such as `[-Path] <String[]>` has an extra distinction: the parameter name can be omitted when its value is supplied in the appropriate position.
`String[]` means the value can be an array of strings; those inner brackets do not mean "optional".
For now, keep writing `-Path` explicitly so the command explains itself. [@PowerShellHelpSyntax]

::: {.tip}
**Tip:** Read help with a question in mind.
Find the command's purpose, identify the argument or option you need, and read one relevant example.
Predict what your version will do before you run it.
You can return for the other options when you have a reason to use them.
:::

## Key Points

- A command name selects an action; arguments provide information for that action.
- Options and parameters change the request, and their syntax belongs to the command you are using.
- Quotation marks can keep spaces inside an argument, but quoting rules differ across shells.
- The shell expands variables, substitutes command output, and in Bash/zsh expands wildcards before the program runs; quotes control which of these happen.
- A path argument tells a command where to look.
- Environment variables are inherited by child programs; `PATH` decides which executable a name runs, and its order settles version conflicts.
- Install tools with a package manager, and open a new shell after an installer changes `PATH`.
- A name may select a built-in, external program, alias, function, or PowerShell cmdlet.
- Use `type`, `Get-Command`, or Command Prompt's help and file-location tools to investigate names.
- Read help as a description of valid commands, not as text to paste without interpretation.

## Level Up

n00bs finish the chapter here.
You can point to the pieces of a command and find help for the ones you do not understand.
Hackers dig deeper.

Choose one command you have used in this chapter and investigate its identity.
In Bash or zsh, compare `type echo` with `type -a echo`.
In PowerShell, inspect `Get-Command echo -All` and compare the result with `Get-Command Write-Output`.
In Command Prompt, compare what `help echo` tells you with what `where.exe cmd.exe` can find.
Explain why a help topic, an alias, and an executable path are different kinds of answer.

Then choose one listing option from the help for `ls`, `Get-ChildItem`, or `dir` that changes only the display or selection of entries.
Predict the difference, run the command, and explain what changed.
Can you make a similar request in another shell without assuming it uses the same syntax?

Finally, find a command nobody has told you about.
In Bash or zsh, `apropos` searches the one-line descriptions of installed manual pages for a keyword, so `apropos directory` lists commands whose descriptions mention directories.
Read the manual page of one that looks interesting and try an option from it. [@ManDbApropos]
In PowerShell, `Get-Command -Noun Item` lists the cmdlets that act on items, and `Get-Help *item*` finds help topics by wildcard. [@PowerShellGetCommand; @PowerShellGetHelp]
In Command Prompt, read the list from `help` and pick a command whose description you do not understand yet.

Explore what your shell shows you about its own work.
In Bash or zsh, `set -x` makes the shell print each command after expansion and before running it; `set +x` turns it off. [@BashSetBuiltin]
In PowerShell, `Trace-Command` can show parameter binding, and `Get-Command -All` with `-ShowCommandInfo` exposes more about how a name resolves.
Which of the transformations in this chapter can you catch in the act?

Then look at your `PATH` critically.
List its directories one per line and check which ones exist.
Is anything on it twice, or in an order you would not have chosen?
Investigate how a tool such as `pipx`, `pyenv`, or `nvm` manages several versions of a language, and explain how it uses `PATH` to do it.

Keep a small note containing the command, what each part means, and where you found the explanation.
That is the beginning of a reference you understand, not just a collection of things to paste.

## Exercises

1. **What does this do?** Predict the output of `printf '<%s>
' "a  b" a  b` in Bash or zsh, paying attention to the double spaces, then run it.
2. **What does this do?** Predict what `Write-Output "$HOME"` and `Write-Output '$HOME'` print in PowerShell, then explain the difference in one sentence.
3. **What is the problem?** A script written for Bash contains `echo %USERPROFILE%` and prints exactly that text. Explain why, and write the line that would work in Bash.
4. **What is the problem?** After installing a tool with a package manager, the shell still says the command is not found. List the three things to check, in order.
5. **Why is it like this?** `Get-ChildItem *.md` lists Markdown files in PowerShell, but the script-block probe shows that the pattern was passed through unchanged. Explain who expanded it.
6. **Why is it like this?** `type -a python3` lists two paths. Explain which one runs when you type `python3`, and how you would run the other one without changing anything.
7. **How do you** find out whether `ls` in your shell is an alias, a function, or a program, and where the program lives if it is one?
8. **How do you** make an environment variable visible to a program started from Bash, and how is that different from PowerShell and Command Prompt?
