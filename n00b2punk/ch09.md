# Programs That Keep Running

Most commands so far finished in a fraction of a second.
Some do not: a download, a build, a server, an editor, or a `sleep` you started by mistake.
While one of them holds the terminal, you cannot type the next command, and when it misbehaves you need to stop it without closing the window.
The operating system tracks every running program, and the shell gives you handles on the ones it started.

The concepts in this chapter are:

- a **process**, its **process ID** (PID), and its parent;
- listing processes and finding one by name;
- **foreground** and **background** execution, and the shell's **jobs**;
- **signals** and the difference between asking a program to stop and forcing it;
- **exit status** of a program that was stopped;
- inspecting **resources**: CPU, memory, load, and disk.

The examples start and stop harmless programs such as `sleep`.
Do not practice stopping on programs you did not start.

## Processes

A **process** is a running program: the code, its memory, its open files, and its connection to a terminal if it has one.
Starting a command creates a new process, and when the command finishes, the process ends and reports an exit status to its **parent**, the process that started it.
Your shell is the parent of everything you run from it, and the shell itself is a child of the terminal application or login manager.

Each process has a number, its **PID**, which is how every other tool refers to it.
PIDs are reused after a process ends, so a number from an hour ago may belong to something else now.

### List Processes

**Bash/zsh:**

```session
$ ps
$ ps aux
$ pgrep -l sleep
```

`ps` alone lists processes attached to this terminal.
`ps aux` lists every process on the system with its user, CPU and memory share, state, and command line; on Linux and macOS the `aux` form works without a hyphen.
`pgrep` searches by name and prints matching PIDs, with `-l` adding the name. [@ProcpsPs; @ProcpsPgrep]

**PowerShell:**

```session
$ Get-Process
$ Get-Process -Name pwsh
$ Get-Process | Sort-Object CPU -Descending | Select-Object -First 5 ProcessName, Id, CPU
```

`Get-Process` returns objects with `Id`, `ProcessName`, `CPU`, and `WorkingSet` properties, so sorting and filtering use the pipeline from Chapter 7.
`$PID` holds the current PowerShell's own process ID. [@PowerShellGetProcess]

**Command Prompt:**

```session
$ tasklist
$ tasklist /fi "imagename eq notepad.exe"
```

`tasklist` lists processes, and `/fi` filters them. [@WindowsTasklist]

## Foreground and Background

A command run normally is in the **foreground**: the shell waits for it, and it owns the terminal's keyboard.
A **background** command runs while the shell returns to the prompt.
The shell keeps a list of the processes it started, called **jobs**, with a small job number for each.

### Bash/zsh

Append `&` to start a command in the background:

```session
$ sleep 60 &
[1] 48213
$ jobs
[1]+  Running                 sleep 60 &
```

The shell prints the job number and the PID and returns the prompt.
`jobs` lists the shell's jobs; `fg` brings the most recent one to the foreground, and `fg %2` picks job 2. [@BashJobControl; @BashJobControlBuiltins]

The other direction works too.
Start `sleep 60` in the foreground, press `Ctrl+Z`, and the shell reports `Stopped`.
The process is paused, not gone.
`bg` resumes it in the background, and `fg` resumes it in the foreground.
That is the accidental `Ctrl+Z` from Chapter 4, and `fg` is the way back.

A background job that writes to the terminal still writes over your prompt, so redirect its output to a file.
And a background job belongs to the shell that started it: closing that terminal usually ends the job.
`nohup command &` starts a command that survives the shell's exit, writing its output to `nohup.out`. [@CoreutilsNohup]

### PowerShell

PowerShell has **jobs** too, but they run in a separate PowerShell process rather than sharing the terminal:

```session
$ $j = Start-Job { Start-Sleep 5; 'finished' }
$ Get-Job
$ Receive-Job $j -Wait
finished
$ Remove-Job $j
```

`Start-Job` runs a script block in the background and returns a job object.
`Get-Job` lists jobs, `Receive-Job` collects their output, and `Remove-Job` cleans up.
In PowerShell 7, `sleep 5 &` at the end of a pipeline does the same as `Start-Job`. [@PowerShellAboutJobs; @PowerShellStartJob]

To start an ordinary program without waiting for it, use `Start-Process`:

```session
$ Start-Process notepad
$ $p = Start-Process sleep -ArgumentList 60 -PassThru
$ $p.Id
```

`-PassThru` returns the process object so that you can inspect or stop it later.
`Start-Process` is not a job; the program runs on its own, and closing PowerShell does not stop it. [@PowerShellStartProcess]

### Command Prompt

`start` launches a program in a new window or, with `/b`, in the same window without waiting:

```session
$ start notepad
$ start /b ping -n 10 localhost
```

Command Prompt has no job list; use `tasklist` and `taskkill` to find and stop what `start` launched. [@WindowsStart]

## Stop a Program

Programs stop for three reasons: they finish, they are asked to stop, or they are forced to.
Prefer them in that order.

`Ctrl+C` in the foreground asks the program to stop, and most programs do.
For a background or unrelated process, you need its PID or name.

### Signals on UNIX

Linux and macOS ask and force with **signals**, small numbered messages the operating system delivers to a process.
Two matter every day:

- **TERM** (15) asks the program to terminate. It can clean up first, and it can ignore the request. `kill` sends this by default.
- **KILL** (9) ends the process immediately. The program gets no chance to save or clean up, and it cannot ignore the signal. [@LinuxSignal7]

```session
$ sleep 60 &
[1] 48301
$ kill 48301
$ jobs
[1]+  Terminated              sleep 60
$ sleep 60 &
[2] 48310
$ kill -KILL %2
```

`kill` accepts a PID or a job number with `%`.
`kill -KILL` and `kill -9` mean the same; `kill -TERM` and `kill -15` are the default.
`pkill sleep` sends a signal to every process with a matching name, and `killall` does the same on systems that have it. [@BashJobControlBuiltins; @ProcpsPgrep]

A process ended by a signal reports an exit status of 128 plus the signal number.
`143` means TERM and `137` means KILL, which is how a script or a log tells you why something stopped. [@BashExitStatus]

`Ctrl+C` sends **INT** (2), which programs treat like TERM.
`Ctrl+Z` sends **TSTP**, the stop behind job control.

::: {.tip}
**Trap:** Reach for `kill -9` last.
A database or editor killed with it can leave a corrupt file or a stale lock.
Send TERM, wait a few seconds, check with `ps` or `jobs`, and only then force it.
:::

### PowerShell

```session
$ Stop-Process -Id 48301
$ Stop-Process -Name sleep
$ Get-Process notepad | Stop-Process
```

`Stop-Process` ends processes by ID, by name, or from the pipeline.
On Windows it is forceful: the process is terminated without a request to close.
`Stop-Process -Confirm` asks before each one, and `-WhatIf` from Chapter 3 works here too. [@PowerShellStopProcess]

On Windows, a graphical program can be asked to close politely with `(Get-Process notepad).CloseMainWindow()`, which is what clicking its close button does.

### Command Prompt

```session
$ taskkill /pid 48301
$ taskkill /im notepad.exe
$ taskkill /im notepad.exe /f
```

Without `/f`, `taskkill` asks a windowed program to close; with `/f`, it forces termination.
`/im` selects by image name, which is the executable's filename. [@WindowsTaskkill]

## Watch the Machine

When everything is slow, the question is which process is using what.

**Bash/zsh:**

```session
$ uptime
$ top
$ free -h
$ df -h
$ du -sh ~/Downloads
```

`uptime` ends with the **load average**: the number of processes wanting to run, averaged over one, five, and fifteen minutes.
A load near the number of CPU cores, which `nproc` prints on Linux, means the machine is busy.
`top` shows a live, sorted list of processes; press `q` to leave it, and read its help with `?`.
`htop`, where installed, shows the same with a friendlier display. [@ProcpsTop; @ProcpsUptime]

`free -h` reports memory on Linux; macOS uses `vm_stat` or Activity Monitor instead.
`df -h` shows disk space by filesystem, and `du -sh` measures one directory tree. [@ProcpsFree; @CoreutilsDf; @CoreutilsDu]

`time command` reports how long a command took, and `timeout 10 command` stops it if it runs longer than ten seconds. [@BashPipelines; @CoreutilsTimeout]

**PowerShell:**

```session
$ Get-Process | Sort-Object WorkingSet -Descending | Select-Object -First 5 ProcessName, WorkingSet
$ Get-PSDrive -PSProvider FileSystem
$ Measure-Command { Get-ChildItem -Recurse }
```

`WorkingSet` is memory in bytes; `CPU` is seconds of processor time used so far.
`Get-PSDrive` shows used and free space per drive, and `Measure-Command` times a script block.
On Windows, **Task Manager** and `Get-Counter` give live numbers; on Linux and macOS, use that system's `top`. [@PowerShellGetProcess; @PowerShellMeasureCommand]

**Command Prompt:**

```session
$ tasklist /v
$ systeminfo
```

`tasklist /v` adds memory and CPU time to the listing, and `systeminfo` reports totals.
For live monitoring, open Task Manager or use PowerShell. [@WindowsTasklist]

## Key Points

- A process is a running program with a PID; `ps`, `Get-Process`, and `tasklist` list them.
- `&` runs a command in the background in Bash and zsh; `jobs`, `fg`, `bg`, and `Ctrl+Z` manage the shell's jobs.
- PowerShell jobs run in a separate process with `Start-Job`, `Receive-Job`, and `Remove-Job`; `Start-Process` launches a detached program.
- UNIX stops programs with signals: TERM asks, KILL forces, and an exit status of 128 plus the signal number tells you which was used.
- `kill`, `Stop-Process`, and `taskkill` end processes by PID or name; try the polite form before the forceful one.
- `top`, `free`, `df`, and `uptime` report resource use on UNIX; `Get-Process` sorted by `CPU` or `WorkingSet` and `Get-PSDrive` do it in PowerShell.

## Level Up

n00bs finish the chapter here.
You can find a process, move it between foreground and background, stop it, and see what the machine is doing.
Hackers look at what a process is doing from the outside.

Explore `/proc` on Linux: `cat /proc/PID/status` and `ls -l /proc/PID/fd` show a process's state and open files.
Compare with `lsof -p PID` on macOS and `Get-Process -Id PID | Select-Object *` in PowerShell.

Try `strace -p PID` on Linux or `dtruss` on macOS to watch the system calls a program makes.
Explain what a program blocked on `read` is waiting for.

Read about **services**: `systemctl` on Linux, `launchctl` on macOS, and `Get-Service` on Windows.
How does a service differ from a background job you started in a shell?

Investigate `nice` and `renice`, and PowerShell's `PriorityClass` property, then explain what priority changes and what it does not.
Then read about **cgroups** and explain how a container limits what a process can use.
